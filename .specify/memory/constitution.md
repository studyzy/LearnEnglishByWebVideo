# LearnEnglishByWebVideo 项目章程

## 核心原则

### I. Chrome扩展规范合规

本项目必须严格遵守Chrome Extension Manifest V3规范:

- **Manifest V3强制**: 所有扩展配置必须使用Manifest V3格式，不得使用已废弃的V2功能
- **Service Worker架构**: 后台脚本必须使用Service Worker替代传统的background pages
- **权限最小化**: 仅请求实现功能所需的最小权限集，遵循最小权限原则
- **CSP合规**: 内容安全策略必须符合Chrome Web Store要求，禁止使用内联脚本和eval()
- **声明式API优先**: 优先使用declarativeNetRequest等声明式API替代程序式API
- **Host权限控制**: 合理使用host_permissions和optional_permissions，避免过度请求

**理由**: Chrome Web Store对Manifest V3的强制要求确保扩展的安全性、性能和用户隐私保护。不合规的扩展将无法发布或被下架。

### II. 代码质量与注释

所有代码必须具有详细的文档注释，确保可维护性:

- **函数注释**: 每个函数必须包含JSDoc风格的注释，说明功能、参数、返回值和异常
- **类注释**: 类必须包含用途说明、职责描述和使用示例
- **复杂逻辑注释**: 算法实现、业务逻辑、Chrome API调用必须附带解释性注释
- **文件头注释**: 每个源文件必须包含版权、作者、创建日期和模块用途说明
- **国际化注释**: 对于i18n消息，必须注释消息的使用场景和上下文
- **TODO标记**: 未完成功能和已知问题必须使用TODO、FIXME或HACK标记并说明原因

**理由**: Chrome扩展的异步特性和复杂的消息传递机制容易导致代码难以理解。详细注释是团队协作和长期维护的基础。

### III. 测试覆盖率要求

单元测试覆盖率必须达到60%以上:

- **核心业务逻辑**: 必须达到80%以上的测试覆盖率
- **Chrome API交互**: 必须模拟Chrome API并编写集成测试
- **消息传递**: content script、background script和popup之间的消息传递必须有端到端测试
- **边界条件**: 网络错误、权限拒绝、存储限制等边界情况必须有测试用例
- **回归测试**: 每个修复的bug必须添加对应的测试用例防止回归
- **持续验证**: CI/CD流程必须包含测试覆盖率检查，低于60%阻止合并

**理由**: Chrome扩展运行在多种页面环境中，测试确保在不同网站和用户场景下的稳定性。60%的覆盖率是质量保证的底线。

### IV. 模块化与职责分离

代码必须遵循清晰的模块化结构:

- **关注点分离**: content scripts、background service worker、popup/options页面必须职责明确
- **可重用组件**: 通用功能必须抽取为独立模块，避免代码重复
- **依赖管理**: 使用现代模块系统(ES6 modules)，避免全局命名空间污染
- **存储抽象**: 对chrome.storage API进行封装，提供统一的数据访问接口
- **消息抽象**: 建立统一的消息协议和处理机制，避免直接使用chrome.runtime.sendMessage

**理由**: Chrome扩展的多上下文特性要求清晰的架构设计，模块化降低耦合度，提高代码的可测试性和可维护性。

### V. 性能与用户体验

必须确保扩展对用户浏览体验的最小化影响:

- **轻量加载**: content scripts必须按需加载，避免在所有页面注入大量代码
- **异步优先**: 所有耗时操作必须异步执行，不阻塞页面渲染
- **内存管理**: Service Worker必须妥善管理生命周期，及时释放不需要的资源
- **存储限制**: 合理使用chrome.storage配额，大数据量考虑使用IndexedDB
- **网络优化**: 最小化远程资源请求，使用缓存策略
- **用户反馈**: 长时间操作必须提供进度提示，错误必须有友好的用户提示

**理由**: 低质量的扩展会显著降低浏览器性能和用户满意度，可能导致用户卸载或差评。

## Chrome扩展特定约束

### 安全要求

- **XSS防护**: 严格验证和转义所有外部输入，特别是注入到页面的内容
- **CSP遵循**: 不使用内联脚本、eval()、new Function()等不安全实践
- **HTTPS强制**: 所有远程API调用必须使用HTTPS协议
- **敏感数据**: 用户凭证和个人信息必须加密存储，不得明文保存
- **权限审计**: 定期审查请求的权限，移除不再需要的权限

### 兼容性要求

- **最低Chrome版本**: 支持Chrome 88+(Manifest V3最低要求)
- **跨平台兼容**: 确保在Windows、macOS、Linux上的Chrome/Edge浏览器正常工作
- **语言支持**: 使用chrome.i18n实现国际化，至少支持英文和中文
- **优雅降级**: 当某些Chrome API不可用时提供降级方案

### 发布规范

- **版本管理**: 遵循语义化版本规范(MAJOR.MINOR.PATCH)
- **变更日志**: 每次发布必须更新CHANGELOG.md，说明新功能、修复和破坏性变更
- **商店审核**: 发布前必须通过内部审查清单，确保符合Chrome Web Store政策
- **隐私政策**: 必须提供清晰的隐私政策文档，说明数据收集和使用方式

## 开发工作流程

### 代码审查要求

- **必要审查**: 所有代码必须经过至少一名其他开发者审查后才能合并
- **审查清单**: 
  - 是否符合Chrome扩展规范
  - 代码注释是否详细
  - 测试覆盖率是否达标
  - 是否存在安全隐患
  - 性能是否可接受
- **自动化检查**: 使用ESLint、Prettier确保代码风格一致性
- **测试门禁**: CI流程必须验证所有测试通过且覆盖率达标

### Git工作流

- **分支策略**: 使用feature分支开发，通过PR合并到main分支
- **提交规范**: 遵循Conventional Commits规范(feat:, fix:, docs:, test:等)
- **提交粒度**: 每个提交应该是一个逻辑完整的变更单元
- **PR描述**: 必须说明变更原因、实现方式和测试方法

### 质量门禁

在以下阶段必须验证质量标准:

1. **开发阶段**: 开发者本地运行测试并检查覆盖率
2. **提交阶段**: Pre-commit hook检查代码格式和基本语法
3. **PR阶段**: CI自动运行完整测试套件和覆盖率检查
4. **合并阶段**: 需要审查者批准且所有CI检查通过
5. **发布阶段**: 手动测试核心功能并验证在实际Chrome环境中的表现

## 治理

### 章程优先级

本章程是项目的最高指导原则，优先于所有其他实践和个人偏好。

### 合规性验证

- **PR审查**: 所有PR必须验证是否符合章程中的每个原则
- **定期审计**: 每季度审计现有代码的章程合规情况
- **违规处理**: 发现违规必须创建issue跟踪，并在下一个sprint内修复

### 修正程序

章程修正需要以下流程:

1. **提案**: 通过issue提出修正提案，说明原因和影响范围
2. **讨论**: 所有核心贡献者参与讨论至少3个工作日
3. **批准**: 需要至少2/3核心贡献者同意
4. **文档化**: 更新此文档并递增版本号
5. **传播**: 更新所有依赖章程的模板和指导文档
6. **迁移**: 如修正涉及代码变更，需要制定迁移计划

### 复杂性证明

当需要违反"性能与用户体验"或"模块化"原则时，必须提供书面证明:

- 说明为什么现有方案不可行
- 列举考虑过的替代方案
- 解释选择该方案的理由
- 评估引入的技术债务和缓解措施

### 版本控制

- **版本格式**: MAJOR.MINOR.PATCH语义化版本
- **递增规则**:
  - MAJOR: 删除或重新定义核心原则，向后不兼容的治理变更
  - MINOR: 新增原则或部分，实质性扩展指导
  - PATCH: 措辞优化、拼写修正、澄清说明
